# DIについて（概要）

DI（Dependency Injection、**依存性注入**）とは、オブジェクトが必要とする部品（依存）を、自分の内部でインスタンス生成したり取得したりするのではなく、**外部から渡してもらう**ようにする設計・実装の考え方です。Webサーバー、CLI、デスクトップ、モバイルなど、**特定のプラットフォームに依存しない**一般的な開発手法です。

この資料ではDI用ライブラリには触れず、**なぜDIをするのか** と **何を指してDIと呼ぶのか** を整理します。Androidにおける典型的なパターンは [次章](./2_AndroidにおけるDI.md) で、本プロジェクトで利用するDIツールである**Koin**の使い方は [3章](./3_Koinを使ったDI.md) で扱います。

---

## 依存とは何か

クラス A がクラス B のインスタンスをフィールドに持ったり、メソッドの引数・戻り値として使ったりすると、「A は B に**依存している**」と言います。

```kotlin
// 画面用クラスがユースケースやサービスに依存している例（概念）
class ExampleViewModel(
  private val postYweetUseCase: PostYweetUseCase,
  private val checkLoginService: CheckLoginService,
)
```

依存自体は悪いものではありません。むしろプログラムは依存の積み重ねです。問題になりやすいのは、**依存の作り方・束ね方** が適切でないときです。

---

## 「自分で作る」と「渡してもらう」

ここでは例として、注文を保存する`OrderRepository`を考えます。`OrderRepository`は「保存する」という振る舞いだけを定めたインターフェースで、`SqlOrderRepository`はそれをSQLで実装した具体クラスです。

```kotlin
// 「保存する」という振る舞いだけを定めたインターフェース
interface OrderRepository {
  fun save(order: Order)
}

// OrderRepositoryをSQLで実装した具体クラス
class SqlOrderRepository : OrderRepository {
  override fun save(order: Order) { /* SQLで保存する */ }
}
```

次のような書き方は、クラス内部でどの実装を使うかを**自分で確定**しています。

```kotlin
// 例：あまり推奨されないパターン（テストや差し替えがしづらい）
class OrderService {
  private val repository: OrderRepository = SqlOrderRepository() // 実装を固定
}
```

一方、次のようにコンストラクタや関数の引数で**外から渡す**ようにすると、`OrderService`は具体的な実装を知らずに`OrderRepository`（インターフェース）だけに依存できます。

```kotlin
class OrderService(
  private val repository: OrderRepository, // インターフェースにだけ依存
)
```

この「依存を外部から渡すこと」を依存性注入と呼び、特にコンストラクタで渡す方法をコンストラクタ注入と呼びます。

`OrderService`がインターフェースにだけ依存していれば、`SqlOrderRepository`を別の実装（例：テスト用のモックや、APIで保存する実装）に差し替えても`OrderService`自体は変更不要です。「誰が`SqlOrderRepository`を`OrderRepository`として渡すか」は、このクラスの外側（アプリ起動時やDIコンテナ）の責務になります。

## DIを採用する主な理由

### 1. テストしやすい

ユニットテストでは、本物のDBやネットワークの代わりに**偽物（モックやスタブ）**を渡したいことが多いです。依存を外から渡せば、テストコードだけで差し替えができます。

### 2. 実装の変更に強い

永続化を SQLiteから APIに変える、といったときも、`OrderService`の修正範囲を小さくできます（インターフェース契約が変わらなければ、`OrderService`は触らない、など）。

### 3. 依存関係が読み取りやすい

コンストラクタを見れば「このクラスは何に依存しているか」が一覧できます。隠れた`getInstance()`やグローバルな参照より、レビューやリファクタがしやすくなります。

### 4. 責務の分離（単一責任に近づく）

「ビジネスロジック」と「部品の生成・生存期間の管理」を分離しやすくなります。

## インターフェースと実装の束ね方

DIを語るときよくセットになるのが、**抽象（インターフェースや抽象クラス）への依存**です。

- **ドメイン層・ユースケース層**などは、可能なら「振る舞いの契約」だけ（インターフェース）に依存させる。
- **インフラ層**が具体的な実装（HTTPクライアント、ファイル、DBドライバなど）を提供する。

「どの実装をどのインターフェースに結びつけるか」を一箇所にまとめると、アプリ全体の配線が見通しやすくなります。その一箇所は、しばしば **コンポジションルート（Composition Root）** と呼ばれます（プログラムのエントリポイント付近：例として`main`、アプリのbootstrap処理など）。

---

## コンポジションルートとは

アプリ起動時など、**依存のグラフを組み立てる最上流**のことです。

- ここでは「`OrderRepository`（インターフェース）には`SqlOrderRepository`（実装）を使う」「同じインターフェースに対し環境別の実装を使い分ける」といった**配線**を宣言する。
- 画面やユースケースのクラスは、配線済みの部品を受け取るだけにする。

DIライブラリ（Koin、Dagger、Guice、Spring など）や**手書きのファクトリ**は、この「配線の宣言」と「必要なときに解決する」作業を支援するための道具です。本質はライブラリ以前に、**依存の方向と境界の設計**にあります。

---

## Service Locatorとは

**Service Locator（サービスロケータ）**は、「欲しい部品を名前や型で**取りにいく**」ための**レジストリ（登録簿）**を用意し、各クラスがそこから`get...()`で取得するパターンです。DIのようにコンストラクタで渡すのではなく、**取得側がレジストリを知っている**点が特徴です。

### ごく簡単な例

起動時に実装を登録し、あとから取り出すイメージです。

```kotlin
// どこか1か所に「取り出し口」を置く（例：シングルトン）
object ServiceLocator {
  private val services = mutableMapOf<Class<*>, Any>()

  fun <T : Any> register(type: Class<T>, instance: T) {
    services[type] = instance
  }

  @Suppress("UNCHECKED_CAST")
  fun <T : Any> get(type: Class<T>): T = services[type] as T
}

// アプリ起動時などに一度だけ登録する
fun bootstrap() {
  ServiceLocator.register(OrderRepository::class.java, SqlOrderRepository())
}

// 利用側：メソッドの中で get する
class OrderService {
  fun placeOrder(itemId: String) {
    val repo = ServiceLocator.get(OrderRepository::class.java)
    repo.save(Order(itemId))
  }
}
```

`OrderService`のコンストラクタは引数を取りません。外から見ると「依存が無いクラス」に見えますが、実際には **`OrderRepository`に依存している** のです。これが **隠れた依存** と呼ばれる理由です。

### コンストラクタ注入と並べると

同じ処理を、前節の **DI（コンストラクタ注入）** で書くと次のようになります。

```kotlin
class OrderService(
  private val repository: OrderRepository,
) {
  fun placeOrder(itemId: String) {
    repository.save(Order(itemId))
  }
}
```

こちらは **コンストラクタを読めば「`OrderRepository`が必要」** と一目で分かります。テストでは`OrderService(FakeOrderRepository())`のように、**レジストリを経由せず**偽物を渡せます。

### Service Locatorで困りやすいポイント（ジュニア向け）

| 観点 | Service Locatorが多いと起きがちなこと |
|------|----------------------------------------|
| 読み取り | クラス宣言だけでは依存が分からない。メソッド本体を追う必要がある |
| テスト | テスト前に`ServiceLocator.register(...)`を整える必要があり、**テスト同士で登録が干渉**しやすい |
| 実行時エラー | 未登録の型を`get`すると実行時に初めて失敗する（コンパイルでは防げない） |

一方で、「どこからでも同じインスタンスが欲しい」だけの小さなユーティリティでは、Locatorで済ませる判断も現場にはあります。**悪いパターンそのもの**というより、**依存を表に出さない代わりにコストが増える**と理解しておくとよいです。

### DIコンテナを「Locatorっぽく」使う場合

Koinや一部のフレームワークでは、どこからでも`get()`や`GlobalContext.get().get()`のように**コンテナに直接取りにいく**書き方もできます。これは仕組みとしてはDIコンテナですが、**クラス設計としてはService Locatorに近い**とみなされることがあります。本インターンでは **コンストラクタ注入 + モジュールでの配線**（[3章](./3_Koinを使ったDI.md)）を基本線にします。

「どちらが絶対正しい」というより、**依存をコンストラクタで宣言できるか**が、保守とテストで効いてきます。

---

## まとめ

| 用語・考え方 | 要点 |
|-------------|------|
| 依存 | あるクラスが別の型を使う関係 |
| DI | 依存を外から渡す（コンストラクタ注入が典型） |
| コンポジションルート | 依存のグラフを組み立てる最上流 |
| 抽象への依存 | 実装差し替え・テストのしやすさにつながる |
| Service Locator | レジストリから`get`する。依存がコンストラクタに出にくい |
